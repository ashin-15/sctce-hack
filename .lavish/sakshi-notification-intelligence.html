Most notifications should leave no durable record

The operating system delivers observations to a user-enabled NotificationListenerService. Sakshi discards unselected packages before reading their extras, then snapshots only bounded standard fields.

Text that does not become a candidate stays transient. A separate storage opt-in allows selected candidates to enter an expiring encrypted inbox. Only user confirmation creates a vault record.

Android service contract

  • System-bound NLS, not an always-running polling service.
  • BIND_NOTIFICATION_LISTENER_SERVICE protects binding; system Settings grants access.
  • POST_NOTIFICATIONS governs Sakshi’s own alerts, not reading other apps.
  • API 24+ callbacks run on main: snapshot, enqueue, return.
  • Wait for connection; active snapshot is not missed history.

Verified Android contract

The deliberate tradeoff:

Process death before selective saving loses RAM observations. Journaling every notification could reduce loss, but would violate the privacy objective. Show coverage uncertainty instead.

Three privacy layers. Three different limits.

System presentation

Visibility and public versions govern what SystemUI reveals on a secure lock screen or during sharing. They are not a universal guarantee that the authorized listener sees the same representation.

Publisher omission

A chat/app lock or preview setting can omit sender and body from the notification itself. WhatsApp Chat Lock documents hidden notification content; Signal documents name/content display options. Sakshi must respect that missingness.

System listener redaction

Android 15 blocks untrusted listeners from unredacted notifications where an OTP is detected. Notification access is not an exception. No trusted-role workaround belongs in Sakshi.

Proposed default: stricter than technical access.

Drop secret notifications. Skip private notification bodies while the device is locked; fail closed if lock state is unknown. Available locked-device preview analysis requires separate opt-in. There is no portable redaction test based on one localized placeholder.

App differences are a test matrix

  • WhatsApp: ordinary/locked chats, reactions, media, groups, summaries.
  • Signal: name+message, name only, no name/message, locked mode, repeat alerts.
  • Telegram: preview/mute preferences, locks, secret/cloud chats, accounts/topics.
  • Instagram/Messenger: no stable notification schema verified here; generic adapter only.

Coverage ends before inference

A source app may not post at all. Work/private profiles, blocked channels, foreground behavior, listener filters, force-stop and OEM app sleep can create gaps.

Report coverage unknown, not “all clear.” Reconnecting cannot retrieve notifications that were removed while Sakshi was absent.

The event is an observation, not a certified message

Retain provenance and uncertainty

  • Observation UUID, collector session/sequence, live versus active-snapshot origin.
  • Package/profile/key/generation, channel, UI group and summary role.
  • Separate system, publisher and collector clocks.
  • Selected item text with exact source path and UTF-16 offsets.
  • Claimed sender, direction, current/historic/summary role and missing fields.
  • Parser/model/calibration versions, truncation, coverage and dedup uncertainty.
  • Consent generation, expiry, review state and canonical-format integrity digest.

No unrelated sibling-message retention.

When one array item becomes a candidate, project only that item and necessary provenance. Do not save every included message, title, contact or attachment just because they arrived in one notification.

Suppress reposts. Preserve real repetition.

Harassment can contain the same sentence repeatedly. A global text hash would erase useful evidence. A notification key identifies a UI record, not a source message.

Cheap decisions first. Models must earn their cost.

Local filter

Exclude unselected and identifiable auth/transaction/player content. Abstain on generic, missing or media-only text. Use language-aware cues, user-selected conversation context and optional RAM-only repetition counters for high-recall triage, not guilt findings.

Measure gate-level false negatives. A classifier cannot recover threats discarded before it runs. Unsupported language, clipping or a model timeout is unknown, never automatically benign.

Small classifier: optional next stage

Evaluate task-specific labels, exact source anchors and per-language calibration. Require conversation/person/source-safe train, calibration and test splits.

Test English, Malayalam, Hindi, Tamil, Telugu, Kannada, Bengali, Marathi, Hinglish, Romanized Indic and code mixing. “Supports multilingual” is not a harassment-quality result.

Laya: research gate, not live baseline

The inspected repository is a non-generative typed decision engine. English is about 421M parameters; multilingual about 322M. It offers choice, bounded score and yes/no probability questions.

The multilingual card describes uncalibrated overconfidence and weak zero-shot typed decisions. The actual ONNX exporter documents substantial INT8 accuracy loss, even at its safer per-tensor default.

Repository, model card and export source

Do not inherit a “33 ms” Android claim.

Published GPU timing is not phone latency, RAM or energy. Laya needs pinned artifacts, tokenizer/head parity, export and quantization evaluation, per-language calibration and real Android budgets. Keep live Laya disabled; begin with user-started analysis of selected candidates only.

Pattern engine: incremental, evidence-linked, incomplete by design

Use selected candidates and confirmed observations for bounded conversation windows: repetition, category changes and possible escalation. A user-entered unwanted-contact boundary is context, not automatically inferred intent.

Observed: retained excerpt. Inferred: possible pressure. Pattern: several independently retained observations. Unknown: complete conversation, human identity or legal conclusion.

Candidate-only retention misses benign-looking buildup and undercounts traffic. Optional persistent metadata counters need separate consent and encryption. Frequency alone does not establish harassment.

Storage consent is separate from access consent

Ordinary observations

RAM only

No text, labels, content hashes or raw event history on disk. Bounded processing, then discard. Session-only candidates are lost when the process dies.

Selected candidates

Separate opt-in

Encrypted short-lived inbox. Proposed starting policy: 24-hour logical expiry, 100 records / 2 MiB cap. Reads exclude expired data immediately; physical cleanup is deferred, not exact flash erasure.

Confirmed evidence

Explicit Save

Immutable selected observation, independent corrections and AI output. User chooses retention and reviewed export. Never silently evict confirmed records or copy unrelated sibling messages.

Strict session key mode

Authentication-gated vault access. No background plaintext spool when the key is unavailable; no biometric prompts from callbacks. Stronger access restrictions reduce passive coverage.

Optional background ingress key

A separate non-auth-per-operation Keystore key can encrypt selected expiring candidates. It also permits app-process decryption: a UI biometric gate is not cryptographic protection against app compromise.

Encryption includes metadata and indexes.

Use app-private no-backup storage, AES-GCM with unique nonces and authenticated record metadata, and versioned integrity hashes. Room/SQLite alone does not encrypt. Exclude cloud and device transfers; allowBackup=false alone has OEM caveats.

A hash checks captured-byte integrity. It does not prove sender authenticity or court admissibility.

User controls and safety defaults
  • Off by default; imports and manual notes work without notification access.
  • App/profile selection, exclusions, pause/revoke and no silent active-inbox replay.
  • Separate retention and locked-preview choices; do not pressure users to weaken messenger privacy.
  • Exact excerpt and uncertainty before confirm/edit/reject; corrections never overwrite the observation.
  • Neutral optional alerts: no sender/body/category, including on the lock screen.
  • No automatic reply, dismissal, mark-read, source navigation, sender contact or report sharing.
  • No cloud fallback, telemetry content or automatic model download on receipt.
  • Clear key-loss, overflow, storage-full and coverage-gap states; never “you are safe.”

Event-driven does not mean battery-free

NLS is system-bound. Keep callbacks short and models cold when idle. No periodic screen scanning, notification polling, permanent wake lock or always-on foreground service by default.

The build gates are behavioral, not just API compilation

  1. Controlled synthetic producer: standard and malformed text, MessagingStyle arrays, summaries, same-ID updates, null senders, private/public versions, cancellation and reconnect.
  2. Real consented app fixtures: known builds/accounts, preview/lock modes, foreground/background, silent/DND/disabled channels, bursts, battery saver and notification permissions.
  3. Privacy verification: no nonselected content or raw notification database, no plaintext job/log/backup leakage, no actions/URI opens/network evidence requests.
  4. Lifecycle races: pause/revoke during queued inference, key unavailable, candidate expiry/rejection, stale jobs, process death and quota overflow.
  5. Semantics and inference: exact anchors, repeated-text multiplicity, no deletion/identity claims, gate recall, per-language quality and export parity.
  6. Phone resource tests: API 30/33/35/36 and current deployment builds as available; Pixel/AOSP-like plus relevant OEM. No desktop benchmark substitution.
Failure modes that must never become confident findings
  • No source post, listener disconnected or private/work profile unavailable → unknown coverage.
  • Generic/locked/opaque/media-only content → abstain, not reconstructed text.
  • Summary duplicates or ambiguous sender/accounts → no fabricated totals or attribution.
  • Unsupported language, clipping, OOM or deferred model → unknown, not benign.
  • Missing key, full storage or tampering → unavailable/error, not plaintext fallback.
  • False positive → review/reject; false negative → no “all clear.”
  • Expiry/rejection with a stale job → drop, never resurrect data.
Minimum defensible implementation

One or two tested source apps, API 30+, bounded structured/generic text, session review plus separately opted-in selective encrypted retention, rules-only suggestions, conservative dedup and user confirmation.

Defer universal app coverage, original-media ingestion, live Laya, LLM narratives and complete notification archiving.

Primary evidence, with its limits intact

  • Android NotificationListenerService: callbacks, system binding, connection, active snapshots, filters, low-RAM/profile limits. Access status and Settings entry verified separately.
  • Notification fields, MessagingStyle.Message, StatusBarNotification, conversations.
  • Android 15 restrictions: OTP redaction and locked private space. Posting permission is separate. Android 17 SMS OTP changes do not establish a blanket E2EE-notification ban.
  • AOSP notification history: optional OEM Settings surface, default 24 hours. Not an ordinary app history grant.
  • Meta Chat Lock; Signal options; Telegram settings schema. Signal full fetch returned 403; official indexed passages were reviewed. No actual installed-app payloads tested.
  • Android Keystore, backup/transfer rules, WorkManager scheduling, Play User Data policy.
  • Specified Laya repository, typed schema, multilingual model card, fine-tuning guide, actual ONNX exporter. Mutable publisher sources, not Sakshi benchmarks. Pin revisions before implementation.

Not built: third-party database scraping, security bypasses, continuous screen capture, automatic full notification archiving, default cloud analysis or automatic legal conclusions.
