Observed gap on the connected CPH2695 phone

The installed Sakshi APK has no libsakshi_llm.so or llama runtime. The AI model screen can select a deterministic canned fallback and still report the model as running. That status is not evidence of Qwen inference.

What needs to connect?

Inference begins only after the user saves/imports text and starts analysis. Notification collection remains passive and unchanged.

Native llama.cpp library

System.loadLibrary("sakshi_llm") → UnsatisfiedLinkError

Source declares JNI methods, but no llama native library is packaged. SessionServices uses rules only; the model screen's fallback can return canned text.

The Android build must contain lib/arm64-v8a/libsakshi_llm.so before the app calls the Qwen engine.

Build sequence

Each step produces evidence that the next layer is real and usable.

Truthful readiness

Separate installed file, runtime present, loading, ready, unavailable and failed. Remove production routing to canned fallback.

Pin native source

Add explicit llama.cpp prepare script with immutable revision, license and source digest; compile through NDK/CMake for arm64.

Prove JNI generation

Build APK with native library. Use synthetic prompts on the phone. Record model digest, load result, output, cold/warm time and memory.

Connect review flow

Call Qwen only from user-started analysis. Validate structured result and exact quote, store provenance, keep user decision separate.

Three code issues to fix with the native bridge

A library file alone will not make this a reliable Qwen integration.

Lifecycle

Avoid synchronous model loading

The current engine loads in its constructor. Readiness refresh can run that constructor. Move hash, GGUF metadata and load work to the analysis/background path with explicit loading status.

Concurrency

Share one heavy-model lock

Qwen's per-engine mutex does not share Whisper's process-wide lock. Coordinate load, generation and unload so two large models cannot overlap.

Prompt format

Apply Qwen's chat template

The current engine concatenates system and user prompts. Pass distinct roles through the model's GGUF chat template, then apply grammar and generation limits.

Native source starting pin: llama.cpp release b6500, commit a7a98e0fffed794396b3fbad4dcdbbc184963645. Treat as a candidate until the arm64 build, Qwen generation, cancellation, and CPH2695 checks pass.

Runtime route comparison

The recommended route follows the existing model manager and local-only app boundary.

A · Package llama.cpp Recommended

Use pinned llama.cpp through Android NDK/JNI and load Sakshi's existing Qwen GGUF.

Cost: native build, ABI, memory and device validation. Benefit: real offline Qwen path under Sakshi's control.

B · Vendor or OPlus API

No supported public Qwen provider interface has been identified in the installed packages or APK.

Cost: unsupported/private app coupling. Benefit: could avoid native packaging if a documented public API appears.

C · Deterministic fallback

Keep the fallback only as a test double. It is not inference and must not be displayed as a running Qwen model.

Cost: no production classification. Benefit: deterministic unit tests.

D · Compact ONNX classifier

A specialist classifier is a possible future alternative after data and tokenizer evaluation.

Cost: different model choice and language coverage. Benefit: finite labels may be easier to calibrate.

Safety and acceptance gates

Real inference is necessary, but it does not by itself prove threat-detection quality.

Threat-language output

possible_threat_language · no_signal · needs_review
  • Use bounded, quoted, untrusted evidence in the prompt; constrain JSON/GBNF and validate exact source quotes.
  • Show positives only as “Possible threat language - AI suggestion”; never call a result credible or dangerous.
  • Qwen self-confidence is not a probability. Do not present categorical no-signal until licensed, conversation-disjoint evaluation supports it.
  • Unqualified language, quoted or denied threats, malformed/truncated output and missing context must abstain or route to review.

Blocking proof

  • 1Runtime: status Ready plus real JNI output; no fallback.
  • 2Pack: app-verified model ID, size and SHA-256.
  • 3Offline: no cloud/network request.
  • 4Device: exact APK/model/runtime versions, ABI, latency and memory receipt.
  • 5Quality: per-language precision, recall, false negatives and abstention on licensed data.
