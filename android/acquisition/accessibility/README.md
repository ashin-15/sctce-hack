# User-started visible text capture

This module exposes generic visible text observations through Android's Accessibility framework. It does not parse or authenticate messages. Every candidate explicitly has unknown sender, direction, and message boundaries. A snapshot can contain navigation labels, dates, incoming text and outgoing text together. Package attribution describes the framework-exposed window, not an authenticated author.

The disabled-by-default service becomes available only after the app's consent disclosure calls `enable()`. The person grants access manually in Android settings, selects chat apps, then starts a five-minute session. The temporary session can remain active while the encrypted vault locks as the person switches to a chat app. Returning to Sakshi must stop capture and require vault authentication before reviewing or importing text. Held snapshots are memory-only and never restored after process death.

`stopSession()` retains the temporary review queue. `stopAndClear()` discards it. Screen-off, device/keyguard lock, service disconnection, interruption, or a restricted-content marker clears everything. Timeout stops new capture but retains snapshots for review. Each new session starts empty. At most 40 snapshots of 8,192 characters are held. Windows exceeding traversal or text limits are rejected rather than presented as complete.

Only WhatsApp, WhatsApp Business, Instagram, Telegram and Signal package probes can be selected in release builds. No package has a validated app-specific parser or coverage guarantee. Apps can expose no text, partial text or restricted text; unknown coverage is reported. Password, editable, invisible and API-34 sensitive nodes are excluded. The service never clicks, scrolls, sends, replies, gestures, reads app databases, takes screenshots, writes text to disk, logs text or sends network requests.

View Once and disappearing content are unsupported. Conservative visible-text/content-description markers stop capture and clear held observations. These heuristics are not exhaustive: there is no reliable cross-app ephemeral-mode flag, and unexposed or localized restrictions may not be detectable. The app disclosure must require the person to use ordinary chats only and avoid opening disappearing-content or View Once screens during capture. No access restrictions are bypassed. Supported share/import workflows remain the appropriate path for source evidence.

Run `:acquisition:accessibility:testDebugUnitTest` and `:acquisition:accessibility:lintDebug` from `android/`. Unit tests verify policy, expiry, limits, restricted-marker clearing and unknown provenance. Real-device validation is still required for each target app and OEM; unit tests do not establish third-party message capture reliability.

## Isolated synthetic device test

`:acquisition:accessibility:assembleDebugAndroidTest` produces `build/outputs/apk/androidTest/debug/accessibility-debug-androidTest.apk`. Its package is `org.sakshi.acquisition.accessibility.test`; its Accessibility service component is `org.sakshi.acquisition.accessibility.test/org.sakshi.acquisition.accessibility.SakshiVisibleTextService`. The fixture activity exists only in this instrumentation APK. The exact test package is selectable only when the library's generated `BuildConfig.DEBUG` is true; release builds exclude it.

The device must be unlocked. Install the test APK, enable its service component, and grant Accessibility access to that isolated test component using Android settings or the test harness. Do not change grants for the Sakshi app or unrelated services. The tests intentionally skip when their grant is absent. Preserve and restore any preexisting system Accessibility settings around the test run, remove the test-only grant, and uninstall the fixture after verification.

Run `:acquisition:accessibility:connectedDebugAndroidTest` or instrument the isolated APK with `androidx.test.runner.AndroidJUnitRunner`. Tests exercise actual framework events against synthetic ordinary text, password/editable fields, a restricted-content label, and an API-34 sensitive node. They verify review retention, clear, revoke and disconnection. They do not lock the person's phone, touch private chats, validate messaging-app parsers, or establish third-party app coverage. A successful test run proves the synthetic window path on that device only.
